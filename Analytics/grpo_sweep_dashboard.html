Reward function architecture

Four complementary signals shape answer quality and output form.

multi-objective
Correctness · dominant

+3.0 exact boxed match · +1.0 within 1% · -0.5 wrong value · -1.0 no boxed answer.

Format · structure

+1.5 valid boxed output · +0.2 partial format cue · -0.5 no attempt.

Reasoning · process proxy

Up to +1.0 for multi-line reasoning and math indicators; -0.5 for degenerate responses under 20 characters.

Length · regularization

0 within 50–2,000 characters · -0.5 too short · -0.3 too long.

Evaluation contract

Documented implementation details

high uncertainty
  • SplitGSM8K test[:50]
  • Decodinggreedy
  • Thinkingenable_thinking=False
  • Matchboxed exact answer
  • Resolution2 percentage points
Statistical caution: around a 76% estimate with n=50, a rough 95% binomial margin is approximately ±12 points. Use the full test split for selection.

Prompt and answer contract

/no_think is prepended to the system prompt, the model is asked to solve step by step, and the final numerical answer must appear inside \boxed{}. Residual <think> blocks are stripped before reward parsing.

Data usage

Runs use the first 500 or 1,000 GSM8K training examples. The documented evaluation uses the first 50 test examples. This deterministic slicing supports reproducibility but should be expanded and randomized for model selection.

Why QLoRA here

efficient

NF4 compresses frozen base weights, while LoRA learns compact rank-decomposition updates. This concentrates trainable capacity in projections that control token mixing and feature transformation.

Winner hypothesis: rank 64 may provide useful capacity under the lower 2e-6 learning rate at this global training scale. The sweep does not isolate rank from LR.

Analytical synthesis

What is observed, what is inferred, and what remains unknown

The five configurations move multiple variables simultaneously. The most useful insight is therefore not a universal hyperparameter optimum, but a set of testable interactions and confidence levels.

Evidence-weighted interpretation
High-confidence observation

run4 owns the measured frontier

observed

76% at 321.4 seconds. Every other recorded 16-GPU run is both slower and less accurate.

Medium-confidence interpretation

Scale changes the useful recipe

interaction

The winner shifts from run3 to run4 across recorded GPU regimes. Global-batch or distributed optimization effects are plausible but not isolated.

Open hypothesis

Exploration may improve data efficiency

test next

run5 reaches 74% with 500 samples, but generation count, LR, batch, accumulation, and steps all change together.

Hyperparameter evidence strength

Confidence reflects experimental isolation, not intuition.

  • 16-GPU run4 is the measured winnerhigh descriptive confidence
  • Low LR × high rank is a useful interactionmedium; pair not isolated
  • More generations improve accuracylow; heavily confounded
  • r64 is independently optimallow; only one r64 run
  • 2e-6 is independently optimallow; only one 2e-6 run

Measurement limitations

selection risk
  • Seedsnot stored
  • Eval size50 in docs, absent from JSON
  • Per-example outputsnot attached
  • Confidence intervalsnot reported
  • World size / SKUabsent from JSON
  • Stability historiesnot in summary
Bottom line: use run4 as the next 16-GPU starting point. Do not yet call 2e-6, r64, four generations, or any single setting universally optimal—the sweep establishes a winning combination, not independent causal effects.
Action plan

Validate, isolate, optimize, then scale

The sequence below minimizes decision risk first, then spends compute on experiments that can explain the winner and improve the recipe.

Prioritized experiment roadmap

Recommended sequence

Validate winner

02

Isolate interaction

Run LR × LoRA grid with every other setting fixed.

Optimize exploration

Compare 4, 8, 16 generations under equal budgets.

04

Scale data / epochs

Only after the stable recipe and evaluation gate hold.

Build a scaling curve

Reward components, KL, clip ratio, entropy, grad norm, completion length, tokens/sec, rollout and all-reduce time.

Test 1 vs 2–3 epochs

Use the validated configuration, shared seeds, full evaluation, and early-stop guards. Do not pre-assign expected accuracy.

Goal: determine whether one epoch under-trains
P2 · scaling

Control global batch

When changing GPU count, preserve global batch first via per-device batch or accumulation; sweep LR as a separate factor.

Goal: separate speedup from optimizer drift
P2 · evaluation

Add stronger math benchmarks

After GSM8K selection stabilizes, add out-of-domain arithmetic and harder reasoning sets to test transfer rather than memorized style.

Goal: verify generalization
