Evidence-based findings

Finding 1

run4 dominates the observed frontier

It combines the highest accuracy (76%) with the lowest raw runtime (321.4 seconds). Its estimated cost is 1.43 GPU-hours if all 16 GPUs were active for the recorded duration.

Finding 2

The best recipe is scale-dependent

The best measured accuracy stays at 76%, but the winner moves from run3 on the prior 4-GPU snapshot to run4 in the 16-GPU artifact. Re-sweeping after a world-size or global-batch change is justified.

Finding 3

Low LR + high rank is a candidate interaction

The winning pair is LR 2e-6 with LoRA r64. Since both variables change together versus run3, this is an interaction hypothesis—not proof that 2e-6 or r64 is independently optimal.

Finding 4

More rollouts remain worth testing

run5's 74% with only 500 samples is encouraging, but it takes 16.1 minutes and uses a different LR, batch, accumulation, and step count. A controlled 4/8/16-generation experiment is needed.

Finding 5

Loss and accuracy rank differently

run1 reports the smallest numerical objective while run4 reports the best accuracy. Select checkpoints with held-out task metrics and use GRPO loss, KL, clipping, reward, and entropy as training diagnostics.

Finding 6

Small accuracy gaps need uncertainty

The JSON does not record evaluation cardinality, seed, confidence intervals, or per-example outcomes. Until those are attached, two- and four-point gaps should be treated as provisional.

Recommended next experiments

High priority

Reproduce run4 before promotion

Repeat the exact run4 configuration across at least three seeds and evaluate each checkpoint on the full GSM8K test split. Save per-example predictions, not only aggregate accuracy.

Outcome: a confidence-backed 16-GPU champion
High priority

Separate LR from LoRA capacity

Run a small 3×2 grid: LR {2e-6, 5e-6, 1e-5} × LoRA rank {32, 64}, holding 4 generations, 1,000 samples, batch 4, accumulation 4, one epoch, and evaluation fixed.

Outcome: clean attribution of the run4 gain
High priority

Record evaluation and hardware metadata

Add seed, eval split and size, world size, node/GPU type, global batch, git commit, package versions, tokens/sec, peak memory, and per-example results to the analytics artifact.

Outcome: auditable cross-scale comparisons
Medium priority

Isolate generation count

Compare 4, 8, and 16 generations at the same LR, LoRA rank, sample count, global batch, optimizer-update budget, seed set, and evaluation protocol.

Outcome: quantify the value and cost of exploration
Medium priority

Build a data scaling curve from run4

Evaluate 500, 1,000, 2,000, and full-train configurations while keeping epochs or optimizer updates explicitly comparable. Report accuracy against both wall time and GPU-hours.

Outcome: choose the best data/compute operating point
Medium priority

Control global batch when scaling

When moving between 4 and 16 GPUs, first hold global batch constant through per-device batch or accumulation changes. Test LR scaling separately instead of assuming a linear rule.

Outcome: distinguish parallel speedup from optimization drift
Follow-up

Export GRPO stability traces

Attach reward components, KL, clip ratio, entropy, gradient norm, completion length, and throughput histories for each run. Summary loss alone cannot diagnose why rankings changed.

Outcome: explainable failures and safer early stopping
After validation

Test additional epochs carefully

Once run4 is reproduced, compare one versus two or three epochs with the same evaluation gate and stability metrics. Avoid projecting an accuracy gain before the controlled result exists.

Outcome: determine whether the one-epoch run is under-trained
