01 — Executive readout

What the repository actually proves

Execution evidence is strong; evaluation evidence is thin. The headline claims, ranked by confidence.

A The one finite result

run1_balanced — train 1.3373, eval 1.4324, perplexity 4.19, 46.6 min, 6.485 samples/s. The only committed finite eval in the repo.

B Lower train loss ≠ better

The other three sweep rows report NaN eval loss. Their lower train losses should not be read as superior generalization — the evaluation simply didn't produce a finite number.

C Config drift in the suite

The current fixed W&B suite diverges from the historical CSV: run3_low_lr now uses LoRA r16 (was r8), and a higher-capacity r32 point was added.

D GRPO runs, but numbers don't ship

GRPO+QLoRA is demonstrated on Qwen3-1.7B / GSM8K across Pytche and Hecate, yet no portable reward/accuracy tables are committed. The 15 / 6 / 40 min figures are narrative, not benchmarks.

E 25 screenshots, two provenance flags

The nemo3nano-ft shots belong to the 8×H100 recipe (not Pytche/Blackwell), and the GRPO doc calls a Qwen3-1.7B + GSM8K text run "multimodal." Both are corrected here.

F The obvious next move

Rerun the four historical Qwen configs through the current finite-eval guard with immutable run manifests before expanding the sweep. Recover validation first, scale second.

G Portfolio skews small

21 of 25 records (84%) use models ≤3B — one 7B VLM and three 30B-A3B Nemotron variants sit above that. Hardware conclusions from small runs may not transfer to 30B-class MoE.

H The one GPU signal

The matched GRPO smoke pair — 4×Rubin ~6 min vs 4×B200 ~15 min — is a 2.5× directional wall-clock ratio. H100 and GH200 have no matched runtime evidence yet.

◇ GPU & size trend insights

  • →

    Small-model iteration dominates the evidence base — good for sweep design, risky to extrapolate to 30B-class models.

  • →

    MoE reframes "size." 30B-A3B is ~30B total but ~3B active per token — routing, memory, and communication all matter; dense-only comparison misleads.

  • →

    GH200 can be under-filled by a 2B QLoRA workload — increase microbatch before accumulation; data movement can bottleneck before compute.

  • →

    H100 evidence is feasibility-heavy. 8×H100 Nemotron/Cosmos runs prove execution but lack matched tokens/s to rank vs B200 or Rubin.

  • →

    Quality must accompany speed. The faster GRPO run isn't automatically better — pair runtime with held-out exact match and reward decomposition.

✓ Minimum fields for the next GPU benchmark

  • ✓

    Same commit, model revision, dataset fingerprint/split, seed, sequence/completion length, global batch, generated-token count.

  • ✓

    Exact GPU SKU/count, node/interconnect, container digest, CUDA/PyTorch/TRL/Transformers versions, attention backend.

  • ✓

    End-to-end and steady-state step time, samples/s or tokens/s, generation tokens/s, peak HBM, per-rank utilization, power, GPU-hours.

  • ✓

    ≥3 repeats per GPU, warm/cold-start separated; report median/p90 plus quality on the same held-out set.

08 — Insight

Method-specific notes

What each fine-tuning method taught, and where its evidence is soft.

SFT / QLoRA GRPO / QLoRA Multimodal / Video
  • →

    Changing rank r16→r8 didn't move two-epoch wall time (~45–47 min) — but other regularization changed at the same time, so rank sensitivity is not isolated.

  • →

    Finite evaluation is the binding data-quality issue. The fixed script wins: safer eval defaults, deterministic seeds, and a failure path for non-finite eval.

  • →

    QLoRA drives memory-efficient adaptation of Qwen, Llama, and Nemotron; pure LoRA appears in the BF16 multimodal / video recipes.

  • →

    Smoke recipe: Qwen3-1.7B, GSM8K-500, LR 5e-6, 2 generations, batch 4 / accum 2, 1 epoch, completion 256, r16/a32/d0.05.

  • →

    Reward = correctness + boxed-format + a line-count heuristic. Log the line-count term separately — it can reward verbosity without correctness.

  • →

    Scaled target: 1,500 examples, 4 generations, 2 epochs, completion 384, batch 2 / accum 4. The ~2h duration is a target, not a measured result.

  • →

    Qwen2.5-VL fixes images to 448×448 and trims dataset length to a multiple of world-size × batch to reduce rank desync.

  • →

    Qwen3-VL fixed-v2 avoids truncating expanded vision-token sequences; memory is held with resolution, batch size, and checkpointing instead.

  • →

    Cosmos video recipes are promising but need stronger run manifests and, in one Hecate doc, reconciliation between YAML structure and Python access (trainer vs data).

09 — Roadmap

Recommended next experiments

Recover validity, then isolate variables, then benchmark hardware — in that order.

1

Validation recovery

Rerun the exact four historical Qwen configs through the fixed evaluation path with seed 42; export run_summary.json per run.

2

One-factor rank sweep

Hold LR / dropout / weight decay constant and compare r8 / r16 / r32 to isolate adapter-capacity effects.

3

Learning-rate sweep

Around the only finite point: 5e-5, 7.5e-5, 1e-4, 1.25e-4 with identical rank/regularization and ≥3 seeds.

4

Controlled GRPO benchmark

Same commit, container digest, dataset fingerprint, seed, and rewards on B200 vs Rubin; log tokens/s, utilization, peak VRAM, GSM8K exact match.

5

SFT → GRPO comparison

Evaluate base, SFT/QLoRA, and SFT+GRPO checkpoints on a held-out math set — does RL add accuracy, or only reward?

6

Immutable provenance

Record commit, script SHA, model revision, dataset fingerprint, GPU name/count, CUDA/PyTorch/TRL versions, container digest, and W&B run ID on every row.

10 — Honesty

Limitations

Stated plainly, because the whole point of this inventory is not to over-claim.

!
Screenshot analysis is context- and provenance-based; exact values were not extracted from plot pixels. Treat screenshot conclusions as qualitative unless backed by committed CSV/JSON.
!
Only four rows have committed machine-readable outcome metrics.
!
Several documents contain screenshots or W&B links without exported numeric history in the repository.
!
Cluster timing statements are not normalized for software versions, token counts, launch overhead, or utilization.
!
Some source files are recipes / templates rather than proof of completed runs; the evidence tier makes that distinction explicit.
